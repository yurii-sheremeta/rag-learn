# Домашнє завдання №1 — Knowledge base: трудове право України

Підготовка першого набору даних для RAG-чатбота-помічника з трудового права України.
Pipeline: `raw sources → normalized documents → chunks → metadata → processed knowledge base`.

---

## 1. Subject area

**Трудове право України** — чатбот-помічник для працівників, HR-фахівців і керівників
малих компаній.

Типові питання, на які має відповідати такий бот:

- Скільки днів щорічної основної відпустки мені належить?
- Чи можна встановити випробувальний термін під час воєнного стану?
- У який строк роботодавець зобов'язаний виплатити розрахунок при звільненні?
- Хто проводить розслідування нещасного випадку на виробництві?
- Що робити, якщо колективний договір не виконується?

Тема обрана свідомо: це **вузька, але змістовна** предметна область із чіткою
внутрішньою структурою (`розділ → глава → стаття → частина`), яку можна відновити
з розмітки джерела й покласти в metadata. Джерела — реальні, публічні й
офіційні, а не синтетичні.

## 4. Pipeline

### Крок 1. Збір (`download_sources.py`)

Завантажує сторінки `/print` із коректним розпакуванням gzip (портал віддає
стиснену відповідь навіть без явного `Accept-Encoding`) і пише
`data/raw/manifest.json` з `document_id`, назвою, типом документа, URL і датою.

### Крок 2. Нормалізація (`prepare_knowledge_base.py`)

1. З повної сторінки вирізається лише контейнер `<div id="article">`
   (зіставленням відкритих/закритих `<div>`) — так відсікається вся навігація,
   меню, футер порталу.
2. `<br>` → перенос рядка, закривні блокові теги → межа абзацу, решта тегів
   видаляється, HTML-entities розкодовуються, нерозривні пробіли нормалізуються.
3. **Прибирається службовий апарат порталу**, який для пошуку є чистим шумом:
   - редакційні примітки у фігурних дужках
     (`{Із змінами, внесеними згідно із Законом № 2352-IX від 01.07.2022}`) —
     зокрема ті, що розтягнуті на кілька абзаців (обробка з відстеженням стану дужок);
   - хронологічні переліки актів про внесення змін (`№ 2048-08 від 18.09.73, ВВР 1973, № 40, ст.343`);
   - технічний штамп картки документа.
4. Відновлюється структура акта: регулярними виразами розпізнаються заголовки
   `Розділ N` / `Глава N` (назва часто йде окремим абзацом) та
   `Стаття N. Назва`. Кожен абзац отримує посилання на главу й статтю, до
   яких належить.
5. Результат зберігається у `data/interim/<document_id>.md` — читабельний
   Markdown, за яким зручно очима перевірити якість нормалізації.

### Крок 3. Чанкінг

**Стратегія: structure-aware packing — `глава → стаття → речення` з перекриттям.**

| Параметр | Значення |
|---|---|
| `TARGET_CHARS` | 800 |
| `MAX_CHARS` | 1000 (жорстка межа) |
| `MIN_CHARS` | 500 |
| `OVERLAP_CHARS` | 150 |

Правила:

- **Межа глави — завжди розрив чанка.** Чанк ніколи не змішує норми з різних глав.
- **Межа статті — розрив**, якщо поточний чанк уже набрав 500 символів.
  Якщо ні, коротка стаття доклеюється до попереднього чанка в межах тієї ж
  глави, а її номер додається до заголовка (`… (а також статті 4, 4-1)`).
  Це прибирає «сміттєві» чанки на 80 символів.
- **Речення не розривається.** Спліттер речень враховує українські правові
  скорочення (`ст.`, `ч.`, `п.`, `абз.`, `тис.`, `грн.`) і номери пунктів
  (`1.`, `12.`), щоб не різати текст після них. Аварійний `hard_split`
  (спершу по комах, далі по словах) застосовується лише до речень, довших
  за бюджет чанка.
- **Перекриття 150 символів** додається лише тоді, коли розрив стався
  *усередині однієї статті* — тобто там, де контекст справді втрачається.
  На межі статей перекриття не потрібне: контекст дає заголовок.
  Перекриття береться цілими реченнями; якщо жодне не вміщується — по межі слова.

### Крок 4. Контекстний заголовок чанка

Кожен чанк починається з рядка-«хлібних крихт»:

```
Про відпустки / Розділ II. ЩОРІЧНІ ВІДПУСТКИ / Стаття 6. Щорічна основна відпустка та її тривалість
```

Це ключове рішення для якості RAG. Без нього чанк на кшталт
*«Тривалість такої відпустки становить 14 календарних днів»* абсолютно
непридатний: незрозуміло, з якого закону, про яку відпустку і для кого йдеться.
Заголовок робить чанк самодостатнім і при читанні, і при ембедингу, і в
відповіді бота (готове посилання на норму). Довжина заголовка врахована
в бюджеті чанка, тому межа 1000 символів не порушується.

## 5. Структура metadata

Формат запису відповідає прикладу із завдання: `chunk_id` і `text` на верхньому
рівні, решта — у `metadata`.

| Поле | Тип | Опис |
|---|---|---|
| `chunk_id` | str | Унікальний ID: `<document_id>_chunk_<NNNN>` |
| `text` | str | Заголовок-хлібні крихти + порожній рядок + текст чанка |
| **metadata** | | |
| `document_id` | str | Ідентифікатор документа |
| `source_file` | str | Шлях до сирого файлу в репозиторії |
| `source_url` | str | Постійне посилання на офіційне джерело |
| `source_type` | str | `html` |
| `title` | str | Повна назва акта |
| `chapter` | str \| null | Розділ / глава акта |
| `section` | str | Стаття, з якої починається чанк |
| `sections` | list[str] | Усі статті, які накриває чанк (зазвичай одна) |
| `article_no` | str \| null | Номер статті (`6`, `42-1`, `173-6`) — зручно для фільтрів |
| `chunk_index` | int | Порядковий номер чанка в документі (з 0) |
| `chunks_in_document` | int | Скільки всього чанків у документі |
| `char_count` | int | Довжина `text` у символах |
| `has_overlap_with_previous` | bool | Чи є перекриття з попереднім чанком |
| `language` | str | `uk` |
| `domain` | str | `labour_law` |
| `document_type` | str | `code` \| `law` |
| `jurisdiction` | str | `UA` |
| `retrieved_at` | date | Дата завантаження джерела |
| `processed_at` | date | Дата побудови чанків |

`source_url` + `article_no` дають боту змогу не просто відповісти, а й
послатися на конкретну статтю з робочим посиланням. `retrieved_at` важливий
тому, що законодавство змінюється: за ним видно, наскільки база застаріла.

## 7. Приклади чанків

### Приклад 1 — типовий чанк (повний запис JSONL)

Класичний випадок: одна стаття цілком вміщується в один чанк.
Це найкращий тип чанка для RAG — точна межа норми, точне посилання.

```json
{
  "chunk_id": "zakon_pro_vidpustky_chunk_0006",
  "text": "Про відпустки / Розділ II. ЩОРІЧНІ ВІДПУСТКИ / Стаття 6. Щорічна основна відпустка та її тривалість\n\nЩорічна основна відпустка надається працівникам тривалістю не менш як 24 календарних дні за відпрацьований робочий рік, який відлічується з дня укладення трудового договору. Промислово-виробничому персоналу вугільної, сланцевої, металургійної, електроенергетичної промисловості, а також зайнятому на відкритих гірничих роботах, на роботах на поверхні шахт, розрізів, кар'єрів і рудників, на будівельно-монтажних роботах у шахтному будівництві, на транспортуванні та збагаченні корисних копалин надається щорічна основна відпустка тривалістю 24 календарних дні із збільшенням за кожних два відпрацьованих роки на 2 календарних дні, але не більше 28 календарних днів.",
  "metadata": {
    "document_id": "zakon_pro_vidpustky",

    "source_url": "https://zakon.rada.gov.ua/laws/show/504/96-%D0%B2%D1%80/print",
    "source_type": "html",
    "title": "Закон України «Про відпустки»",
    "chapter": "Розділ II. ЩОРІЧНІ ВІДПУСТКИ",
    "section": "Стаття 6. Щорічна основна відпустка та її тривалість",
    "sections": ["Стаття 6. Щорічна основна відпустка та її тривалість"],
    "article_no": "6",
    "chunk_index": 6,
    "chunks_in_document": 80,
    "char_count": 766,
    "has_overlap_with_previous": false,
    "language": "uk",
    "domain": "labour_law",
```

відфільтрувати саме цю норму, `source_url` — дати посилання у відповіді.

### Приклад 2 — пара чанків із перекриттям усередині однієї статті

Стаття 2-1 КЗпП надто довга для одного чанка, тому розрізана. Кінець
`kzpp_chunk_0004` (991 символ):

```
… часті у страйку, звернення або наміру звернення до суду чи інших органів за
захистом своїх прав або надання підтримки іншим працівникам у захисті їхніх прав,
повідомлення про можливі факти корупційних або пов'язаних з корупцією правопорушень,
інших порушень Закону України "Про запобігання корупції",
```

Початок `kzpp_chunk_0005` (753 символи, `has_overlap_with_previous: true`):

```
КЗпП України / Глава I. ЗАГАЛЬНІ ПОЛОЖЕННЯ / Стаття 2-1. Рівність трудових прав громадян України, недопущення дискримінації у сфері праці

прав, повідомлення про можливі факти корупційних або пов'язаних з корупцією
правопорушень, інших порушень Закону України "Про запобігання корупції", а також
сприяння особі у здійсненні такого повідомлення, за мовними або іншими ознаками,
не пов'язаними з характером роботи або умовами її виконання. Не вважаються
дискримінацією у сфері праці встановлені цим Кодексом та іншими законами…
```

**Коментар.** Наочно видно роботу перекриття: хвіст попереднього чанка
повторюється на початку наступного, тому норму не «розірве» навпіл під час
пошуку. Заголовок відновлює контекст статті, який інакше був би втрачений —
без нього другий чанк починався б словом «прав» і був би нечитабельним.
Це також приклад найслабшого місця пайплайну: речення в цій статті довше
за 1000 символів, тому розрив довелось зробити всередині нього
(див. пункт 1 у висновках).

### Приклад 3 — чанк, що склеїв кілька коротких статей

`kzpp_chunk_0011`, 771 символ, `sections` містить три статті:

```
КЗпП України / Глава I. ЗАГАЛЬНІ ПОЛОЖЕННЯ / Стаття 3. Регулювання трудових відносин (а також статті 4, 4-1)

Особливості та порядок регулювання трудових відносин суб'єктів малого та середнього
підприємництва визначаються главою III-Б цього Кодексу. Дія цього Кодексу та
законодавства про працю не поширюється на відносини між гіг-спеціалістами та
резидентами Дія Сіті, визначені Законом України "Про стимулювання розвитку цифрової

Професія (вид занять) - це сукупність близьких за трудовими функціями видів трудової
діяльності, що можуть вимагати певної професійної...
```

**Коментар.** Три сусідні короткі статті однієї глави об'єднані в один чанк
нормального розміру замість трьох огризків по 150–250 символів. Заголовок
чесно перелічує всі статті, а повний перелік лежить у `metadata.sections` —
бот не «припише» текст статті 4 статті 3.

## 8. Висновки

### Що вийшло добре

- **Реальні офіційні джерела**, а не синтетика; pipeline відтворюваний однією
  командою, з фіксацією URL і дати завантаження в `manifest.json`.
- **Structure-aware чанкінг замість «різати кожні 800 символів»**. Межі
  чанків збігаються з межами норм права, тому чанк майже завжди = одна думка
  законодавця. 97% чанків у цільовому діапазоні 500–1000, жоден не перевищує 1000.
- **Контекстний заголовок у кожному чанку** зробив фрагменти самодостатніми.
  Це найбільший внесок у якість: без нього більшість чанків КЗпП були б
  беззмістовними уривками.
- **Ретельне очищення джерела.** Найбільше роботи забрали не теги, а службовий
  апарат порталу: примітки у фігурних дужках, розтягнуті на кілька абзаців, і
  сотні рядків хронології змін. Без їх видалення близько чверті чанків КЗпП
  були б переліками на кшталт «№ 2048-08 від 18.09.73».
- **Перекриття застосовується вибірково** — лише там, де розрив стався
  всередині статті (372 чанки), а не механічно скрізь. Це економить місце
  й не дублює контекст там, де його дає заголовок.
- **Валідація як окремий крок.** `validate_chunks.py` не просто рахує чанки,
  а перевіряє, що задеклароване перекриття справді присутнє в попередньому
  чанку (365/372) і що в тексті не лишилось розмітки.

### Що треба покращити

1. **19 чанків (2.5%) обриваються посеред речення.** Це наслідок аварійного
   `hard_split` на реченнях довжиною понад 1000 символів — у КЗпП такі
   трапляються (перелік підстав для звільнення в статті 43). Правильніше було б
   різати такі речення по нумерованих пунктах (`1)`, `2)`, `3)`), а не по комах.
2. **Не оброблено внутрішні перехресні посилання.** Текст рясніє відсиланнями
   «у випадках, передбачених статтею 40 цього Кодексу». Для бота це глухий кут:
   чанк зі статтею 40 не буде піднятий за таким запитом. Наступний крок —
   витягати номери згаданих статей в окреме поле metadata `references` і
   використовувати їх для дозбирання контексту.
3. **23 чанки коротші за 500 символів.** Це короткі статті цілком (напр.
   стаття 20 «Звіти про виконання колективного договору»). Формально вони
   не в діапазоні, змістовно — самодостатні. Але їх варто позначити окремим
   прапорцем, щоб не плутати з дефектними.
4. **Немає підрахунку токенів.** Розмір міряється в символах, а ліміт
   embedding-моделі — у токенах. Для української мови співвідношення гірше,
   ніж для англійської (приблизно 2.5–3 символи на токен), тож перед
   ембедингом варто перерахувати й перевірити реальні ліміти.
5. **Дублювання норм між документами.** Частина положень про відпустки є
   і в КЗпП, і в Законі «Про відпустки». Пошук видаватиме дві схожі відповіді,
   іноді в різних редакціях. Потрібна або дедуплікація, або явна пріоритезація
   спеціального закону над кодексом у промпті.
6. **База застаріває.** Законодавство змінюється, а `retrieved_at` фіксований.
   Потрібен періодичний перезапуск pipeline і порівняння хешів текстів,
   щоб оновлювати лише змінені документи.

# Домашнє завдання №2 — Semantic retrieval layer

Надбудова над knowledge base: `chunks.jsonl → embeddings → FAISS index → top-k search`.

## 9. Модель ембедингів

| Параметр | Значення |
|---|---|
| Модель | `intfloat/multilingual-e5-base` |
| Розмірність | 768 |
| Префікси | `passage: ` для чанків, `query: ` для запиту |
| Нормалізація | так (вектори одиничної довжини) |
| Індекс | `faiss.IndexFlatIP` — точний перебір |
| Метрика | косинусна подібність, діапазон `[-1, 1]` |
| Векторів | 763 |

**Чому не `all-MiniLM-L6-v2`**, рекомендована в завданні: вона натренована лише
на англійській. На українському юридичному тексті це не «трохи гірше», а
зламаний retrieval. `multilingual-e5-base` тренована саме під багатомовний
пошук і дає адекватні результати українською.

**Чому E5-префікси обов'язкові.** Моделі сімейства E5 навчені з розділенням
ролей: документ кодується як `passage: …`, запит як `query: …`. Без префіксів
якість помітно падає. Щоб їх неможливо було випадково розсинхронізувати,
`build_index.py` записує їх у `index/config.json`, а `retrieval.py` читає
звідти — запит фізично не може бути закодований інакше, ніж документи.

**Чому `IndexFlatIP`, а не IVF/HNSW.** На 763 векторах точний перебір займає
мікросекунди; наближені індекси тут лише додали б похибку без жодного виграшу.
А оскільки вектори нормалізовані, скалярний добуток дорівнює косинусній
подібності — score читається інтуїтивно, на відміну від `IndexFlatL2`, де
менше значення означає ближче.

## 10. Як користуватися

```bash
pip install -r requirements.txt
```

```bash
python scripts/build_index.py
```

```bash
python scripts/retrieval.py "чи оплачується робота в нічний час" -k 5
```

Без аргументів `retrieval.py` переходить в інтерактивний режим. Прапорець

Відтворити звіти:

```bash
python scripts/run_test_queries.py && python scripts/evaluate_retrieval.py
```

Перше збирання індексу завантажує модель (~1.1 ГБ) і кодує 763 чанки — близько
5–6 хвилин на CPU. Далі пошук миттєвий.

## 11. Тестування

10 запитів, сформульованих так, як їх поставив би працівник, а **не** цитатами
із законів. Це принципово: якби ми питали словами статті, кожен top-1 був би
тривіальним влучанням і аналізувати не було б чого.

Повні результати з metadata — [`outputs/retrieval_examples.md`](outputs/retrieval_examples.md).

Крім якісних коментарів, `evaluate_retrieval.py` міряє річ, яку не видно з
очей: для кожного запиту заздалегідь відома стаття, що на нього відповідає, —
тож можна порахувати, на якому місці вона реально опиняється.

| Метрика | Значення |
|---|---|
| recall@1 | **50%** (5 із 10) |
| recall@3 | **90%** (9 із 10) |
| recall@5 | 90% |
| recall@10 | 90% |

Розподіл оцінок: 4 запити `relevant`, 6 `partially relevant`, жодного повністю
провального — але «partially» тут майже завжди означає одне й те саме.

## 12. Висновки

### Де retrieval працює добре

**Потрібний закон визначається майже завжди.** У 9 із 10 запитів правильна
стаття потрапила в top-3, і в жодному випадку система не пішла шукати
відповідь не в тому акті. Для корпусу з шести схожих за стилем законів це
хороший результат.

**Запити-визначення — ідеальний випадок.** «Що таке мінімальна заробітна
плата» дає точну статтю 3 на першому місці зі score 0.883. Стаття з
визначенням терміна коротка, самодостатня і лексично близька до питання.

**Розмовне формулювання не заважає — доки не розходиться з термінологією.**
«Мене змушують вийти на роботу у вихідний» знайшло статтю 71 про заборону
роботи у вихідні, хоча в запиті немає жодного юридичного терміна. Модель
справді працює семантично, а не за збігом слів.

**Кращий результат набору — питання про розрахунок при звільненні.** Три
чанки в top-3 склали повну відповідь: обов'язок (ст. 47), строк (ст. 116) і
відповідальність за затримку (ст. 117). Саме так має виглядати контекст,
який далі піде в LLM.

**Контекстний заголовок із ДЗ №1 виправдав себе.** Кожен чанк несе рядок
`Акт / Глава / Стаття`, тож навіть фрагмент із середини статті лишається
атрибутованим, а у видачі одразу видно норму й посилання на джерело.

### Де retrieval ламається

**1. Правильна норма систематично опиняється на 2-му місці, а не на 1-му.**
Це головна знахідка: recall@1 = 50%, але recall@3 = 90%. У п'яти запитах із
десяти top-1 — сусідня стаття тієї ж теми, а точна відповідь одразу під нею.
Приклад: на «скільки годин на тиждень я маю працювати» перше місце посіла
стаття 52 (п'ятиденний і шестиденний тиждень), а стаття 50 з прямою нормою
«не більше 40 годин» — друге. Причина видна із заголовка: у ст. 52 в назві
є і «робочий тиждень», і «тривалість», тобто вона лексично ближча до запиту,
хоча відповіді не містить. Практичний висновок: **k=1 для цієї бази
непридатне, мінімум k=3**, а правильне рішення — reranker (наприклад
cross-encoder), який переставить top-10 за реальною релевантністю.

**2. Дублювання норм між КЗпП і спеціальними законами підтвердилось.** Це
було передбачено у висновках ДЗ №1 — і проявилось буквально. На запит про
мінімальну зарплату top-1 (ст. 3 Закону «Про оплату праці») і top-2 (ст. 95
КЗпП) починаються **однаковим реченням**, а score відрізняється на 0.001. Те
саме з нещасними випадками: ст. 22 Закону «Про охорону праці» і ст. 171 КЗпП.
Один слот із трьох витрачається на дубль. Потрібна або дедуплікація за
схожістю векторів, або явна пріоритезація спеціального закону над кодексом.

**3. Довгі статті-переліки семантично невидимі — найважча знахідка.**
Запит «чи можу я взяти відпустку за свій рахунок на два тижні» не підняв
статті 25 і 26 Закону «Про відпустки» навіть у топ-10, хоча це буквально
профільна норма. Причина не в моделі, а в чанкінгу: стаття 25 розрізана на
**10 чанків**, кожен з яких — уривок переліку категорій («пенсіонерам за
віком… ветеранам праці… сумісникам…»). Визначальне речення «відпустка без
збереження заробітної плати надається в обов'язковому порядку» розчинилось
серед перерахувань, і жоден окремий чанк не виглядає як відповідь на питання.
Врятувала видачу стаття 84 КЗпП на 2-му місці — та сама норма, але
сформульована компактно.

Це прямий аргумент за **contextual retrieval**: до кожного чанка-фрагмента
переліку варто додавати одне речення, що описує, частиною чого він є.

**4. Розрив усередині статті дає нечитабельний top-1.** На питання про роботу
у вихідний перше місце посів чанк, що починається словами «вантажно-
розвантажувальних робіт з метою запобігання…» — середина переліку винятків.
Стаття вгадана точно, але саме речення із забороною лишилось у сусідньому
чанку. Це ті 2.5% обірваних чанків із ДЗ №1, які тепер видно в дії.

**5. Скори стиснуті у вузькому діапазоні.** Усі top-1 лежать між 0.851 і
0.897, а різниця між правильною і хибною відповіддю часто менша за 0.01. Це
означає, що **поріг відсікання за score побудувати не можна** — не вийде
сказати «нижче 0.8 не показуємо». Наслідок для ДЗ №3: система не зможе
розпізнати, що відповіді в базі немає, і чесно сказати «не знаю».

### Що робити далі

1. **Reranker поверх top-10** — найдешевший спосіб підняти recall@1 з 50%.
2. **Дедуплікація** близьких чанків із різних актів перед видачею.
3. **Contextual retrieval** для статей-переліків (пункт 3 вище).
4. **Гібридний пошук** — додати BM25 поряд із векторним: запити з точними
   номерами («стаття 116») і рідкісними термінами лексичний пошук бере краще.
5. **Перевірити гіпотезу про заголовок.** Кейс зі статтею 52 натякає, що
   breadcrumb-заголовок впливає на ембединг сильніше, ніж очікувалось —
   іноді на користь, іноді на шкоду. Це перевіряється прямим експериментом:
   зібрати другий індекс без заголовків і порівняти recall на тому самому
   наборі запитів.

# Домашнє завдання №3 — Покращення retrieval pipeline

Мета — не додати техніку, а довести числом, що пошук став кращим.

## 13. Що змінилось у пайплайні

Baseline (ДЗ №2) робив один крок: bi-encoder → top-3. Improved вставляє між ними
три стадії й бере ширший захват кандидатів.

```
запит
  ↓
bi-encoder → 20 кандидатів        (було: одразу 3)
  ↓
metadata-фільтри                  ← номер статті / акт із самого запиту
  ↓
дедуплікація між актами           ← прибирає дублі КЗпП ↔ спецзакон
  ↓
cross-encoder reranker            ← переставляє те, що лишилось
  ↓
top-3
```

Кожну стадію можна вимкнути окремо (`--no-filters`, `--no-dedup`,
`--no-rerank`) — саме це дозволяє виміряти внесок кожної, а не лише
загальний результат.

## 14. Результат

|---|---|---|---|

| + дедуплікація | 50% | 90% | 0 |

## 15. Metadata filtering

Перше, що з'ясувалось: **чотири з шести полів метаданих у нашому корпусі —
константи**.

| Поле | Унікальних значень |
|---|---|
| `language`, `domain`, `jurisdiction`, `source_type` | по 1 |
| `document_type` | 2 (`code` 463 / `law` 300) |
| `document_id` | 6 |
| `article_no` | заповнено у 758 із 763 |

Фільтр `domain=labour_law`, який напрошується із формулювання завдання, не
відсіяв би **жодного** чанка: корпус однорідний за задумом. Тому фільтрувати
треба за тим, що справді варіюється, і так, щоб фільтр розв'язував виміряну
проблему. Реалізовано три:

**1. `article_no` із тексту запиту.** Регулярка виловлює «стаття 116», «ст. 50»,
«статті 40» і жорстко звужує пошук до чанків цієї статті. Лікує знахідку ДЗ №2
«точні номери статей губляться».

**2. `document_id` — маршрутизація за назвою акта.** Якщо запит містить «КЗпП»,
«закон про охорону праці», «воєнного стану» — пошук іде лише в цей акт.
Свідоме обмеження: маршрутизація спрацьовує **тільки на явну назву акта**, а не
на тему. Слово «відпустка» зустрічається і в КЗпП, і в спеціальному законі —
вгадувати один із них означало б сховати другий.

**3. Дедуплікація за `document_type`.** Прибирає майже однакові чанки з різних
актів, лишаючи спеціальний закон замість кодексу.

### Чому дедуплікація не могла бути «просто порогом»

Найцікавіший технічний момент завдання. Виміряні косинусні схожості на нашому
корпусі:

| Пара | Схожість |
|---|---|
| Сусідні чанки **однієї** статті | **0.967** |
| Справжній дубль між актами (ст. 3 закону ↔ ст. 95 КЗпП) | **0.944** |
| Незв'язані чанки | 0.828 |

Дублі, які треба прибрати, схожі **менше**, ніж сусідні чанки, які треба
зберегти. Жоден єдиний поріг їх не розділяє: поставивши 0.94, ми знищили б
корисні продовження статей — а саме вони дали найкращий результат ДЗ №2
(запит про розрахунок при звільненні, де top-3 склали три взаємодоповнювані
норми).

Рятують метадані. Схожість вирішує **лише між чанками з різними
`document_id`**; усередині одного акта не відкидається нічого. Це і є
metadata filtering, що виконує реальну роботу, а не існує для галочки.

### Фільтри в дії

Оскільки з десяти оцінювальних запитів акт називає лише один, а номер статті —
жоден, фільтри показані на окремих запитах:

| Запит | Виявлені фільтри | Кандидатів |
|---|---|---|
| «що каже стаття 116 про строки розрахунку» | `article_no=116` | 20 → 1 |
| «які обов'язки роботодавця встановлює закон про охорону праці» | `document_id=zakon_pro_ohoronu_praci` | 20 → 15 |
| «стаття 40 КЗпП підстави звільнення» | `article_no=40, document_id=kzpp` | 20 → 5 |

## 16. Reranking

### Bi-encoder проти cross-encoder

Це різниця, заради якої техніка й працює.

**Bi-encoder** (наш `multilingual-e5-base`) кодує запит і документ **окремо**.
Вектор чанка рахується один раз при індексації, вектор запиту — при пошуку,
далі порівнюється лише результат. Документ ніколи «не бачить» запиту. Тому це
швидко (одне множення матриці на всі 763 чанки), але грубо.

**Cross-encoder** (`BAAI/bge-reranker-v2-m3`) подає пару «запит + документ» в
модель **разом, одним входом**, і оцінює саме їхнє відношення. Модель бачить,
на які слова запиту відповідають які слова документа. Значно точніше — і
принципово не піддається попередньому обчисленню.

Наслідок для архітектури: cross-encoder **не можна** пустити по всій базі. Наш
reranker — це XLM-RoBERTa-large на 568 млн параметрів; повний прохід по 763
чанках на CPU зайняв би 10–20 хвилин на один запит. Тому схема завжди
двоступенева: дешевий bi-encoder звужує 763 → 20, дорогий cross-encoder
переставляє ці 20.

### Чому саме reranking мав спрацювати

Це передбачалось із чисел ДЗ №2, а не обиралось навмання. Розрив
`recall@1 = 50%` при `recall@3 = 90%` означає буквально: **правильна відповідь
майже завжди вже у видачі, просто не перша**. Reranker'у не треба нічого
знаходити — лише переставити. Це ідеальна для нього ситуація, і саме тому
приріст вийшов таким великим.

Приклад. Запит «скільки годин на тиждень я маю працювати»:

| | Baseline | Improved |
|---|---|---|
| top-1 | ст. 52 «П'ятиденний і шестиденний робочий тиждень» | ст. 50 «Норма тривалості робочого часу» |
| | лексично ближча, відповіді не містить | «не може перевищувати 40 годин на тиждень» |

Bi-encoder піднімав ст. 52, бо в її **заголовку** є і «робочий тиждень», і
«тривалість». Cross-encoder прочитав запит разом із текстом і побачив, що
відповідь на «скільки годин» — у ст. 50.

## 17. Висновки

### Що дало найбільший ефект

**Reranking — з великим відривом: +30 відсоткових пунктів окремо.** Фільтри й
дедуплікація самі по собі дали 0. Це не означає, що вони марні — див. нижче,
але як засіб підняти recall@1 вони не працюють.

**Стадії взаємодіють.** Reranking окремо дав 80%, усі три разом — 90%. Тобто
дедуплікація додала ще 10 в.п., але **тільки в парі з reranker'ом**. Механізм:
дедуплікація прибирає дубль зі списку кандидатів, звільняючи місце, і
reranker отримує інший набір для переставляння. Ізольовано ця стадія нічого не
змінює, бо просто прибрати дубль з 2-ї позиції не робить 1-шу правильною.

Це головний методологічний висновок: **абляція по одній стадії недооцінює
внесок**, якщо стадії впливають одна на одну. Тому в таблиці є і рядки окремих
стадій, і рядок повного пайплайна.

### Чого не виправив жоден із методів

Запит «чи можу я взяти відпустку за свій рахунок на два тижні» лишився
провальним: статті 25 і 26 Закону «Про відпустки» не з'явились у top-3 ні
до, ні після. Причина відома ще з ДЗ №1 — стаття 25 розрізана на **10
чанків-переліків категорій**, і визначальне речення розчинилось серед
«пенсіонерам… ветеранам праці… сумісникам…».

Це принципове обмеження: reranker переставляє те, що знайшов bi-encoder. Якщо
правильний чанк не потрапив у 20 кандидатів, переставляти нічого. **Дефект
чанкінгу не лікується на етапі пошуку** — потрібен contextual retrieval або
переріз статей-переліків.

### Чесно про статистику

Десять запитів — дуже мала вибірка. Стрибок recall@1 з 50% до 90% — це
**чотири запити**. Довірчий інтервал за такої кількості спостережень
величезний, тож правильне формулювання: числа показують напрямок і узгоджуються
з механізмом, який ми можемо пояснити, але вони не є статистичним доказом.
Для надійного висновку потрібен набір хоча б на 100 запитів із розміченими
правильними статтями.

### Ціна

| | Baseline | Improved |
|---|---|---|
| Час на запит (CPU) | ~0.1 с | ~20 с |
| Моделей на диску | 1.1 ГБ | 1.1 + 2.2 ГБ |
| Кандидатів оброблено | 3 | 20 |

Двохсоткратне сповільнення — реальна ціна. Для навчального проєкту прийнятна,
для продакшну довелось би брати меншу модель reranker'а
(`bge-reranker-base`, 278M) або GPU. Цю ціну варто знати наперед: reranking
завжди купує якість за латентність.

# Домашнє завдання №4 — Grounded QA поверх retrieval

Остання ланка: знайдені чанки йдуть у промпт, модель відповідає **тільки**
з них і чесно каже «не знаю», коли контексту бракує.

## 19. Архітектура

```
питання працівника
  ↓
retrieval із ДЗ №3            bi-encoder → фільтри → дедуплікація → reranker
  ↓
top-3 чанки з метаданими
  ↓
промпт: роль + правила + контекст + питання
  ↓
claude-opus-5, adaptive thinking
  ↓
відповідь із посиланнями [Стаття N Акт, chunk_id]
```

Ключова деталь реалізації — **кеш retrieval**. Ітерації промпта не змінюють
знайдені чанки, тому пошук виконується один раз
(`scripts/build_retrieval_cache.py`), а всі подальші прогони промптів беруть
контекст із `outputs/retrieval_cache.json`. Без цього кожна правка промпта
запускала б cross-encoder заново — найдорожчу частину пайплайна.

## 20. Як fallback врешті влаштований

У висновках ДЗ №2 записано, що поріг за score побудувати не можна: усі top-1
bi-encoder'а лежали в смузі **0.851–0.897**, а правильна й хибна відповіді
відрізнялись на соті. Це лишається правдою для bi-encoder'а.

**Але cross-encoder із ДЗ №3 змінив картину.** Його скори на тих самих
десяти питаннях:

| Питання | Тип | Скор top-1 |
|---|---|---|
| Скільки днів відпустки | є в корпусі | 0.998 |
| Розрахунок при звільненні | є в корпусі | 0.994 |
| Максимальний робочий тиждень | є в корпусі | 0.960 |
| Звільнення на лікарняному, воєнний стан | кілька статей | 0.412 |
| Відпустка в Польщі | пастка | 0.324 |
| Переформульоване про відпустку | retrieval промахнувся | 0.292 |
| Робота на двох роботах | слабкий retrieval | 0.147 |
| Відпустка за свій рахунок | слабкий retrieval | 0.129 |
| Податки із зарплати | немає в корпусі | 0.028 |
| Судовий збір | немає в корпусі | 0.022 |

Діапазон — від 0.022 до 0.998, тобто у **45 разів**. Reranking дав побічний
ефект, якого ми не планували: **придатний сигнал впевненості**.

Проте поріг сам по собі проблему не вирішує. Питання поза корпусом чисто
відсікаються (< 0.03), а от середня смуга 0.13–0.41 змішана: там і питання
про звільнення на лікарняному (0.412), на яке відповідь **є** в контексті,
і пастка про Польщу (0.324), на яку відповідати не можна. Поріг на 0.5
відмовив би на обох.

Окремо повчальний випадок — переформульоване питання про відпустку (0.292).
Скор середній, у контексті навіть є потрібна стаття 10 — але **не той її
фрагмент**, що містить норму про шість місяців. Ні скор, ні номер статті
цього не показують; побачити це можна лише прочитавши текст.

Тому конструкція така: **дуже низький скор — технічний фільтр, середня смуга —
рішення моделі**. Модель бачить текст, а не число, тож здатна відрізнити
«та сама стаття» від «та сама норма».

## 21. Prompt template

Фінальна версія (`v3` у `scripts/prompts.py`):

```
Ти асистент з трудового права України. Відповідаєш працівникам
простою мовою, спираючись лише на надані витяги з нормативних актів.

ПОРЯДОК РОБОТИ
Спершу перевір, чи контекст справді відповідає на поставлене питання.
Контекст дібрано автоматичним пошуком, тому він регулярно буває
частково або повністю нерелевантним — висока схожість не означає, що
відповідь усередині. Наявність у контексті слів із питання не є
відповіддю на нього.

ЯКЩО КОНТЕКСТ ВІДПОВІДАЄ НА ПИТАННЯ
- Відповідай стисло, по суті, без переказу всієї статті.
- Після кожного твердження став посилання у форматі
  [Стаття N Назва акта, chunk_id].
- Якщо норму доповнює друга стаття з контексту — згадай і її.

ЯКЩО КОНТЕКСТ НЕ ВІДПОВІДАЄ АБО ВІДПОВІДАЄ ЛИШЕ ЧАСТКОВО
Почни відповідь рядком:
"У наданих документах недостатньо інформації, щоб відповісти на це питання."
Далі одним реченням поясни, чого бракує, і, якщо контекст усе ж містить
дотичну норму, назви її окремо як часткову інформацію.

ЗАБОРОНЕНО
- Використовувати знання поза контекстом. Ти знаєш українське трудове право
  з навчання — ці знання тут не діють. Питання про інші країни, про податкове,
  процесуальне чи будь-яке інше законодавство поза наданими витягами завжди
  отримують відповідь про недостатність інформації.
- Вигадувати номери статей, назви актів або chunk_id, яких немає в контексті.
- Відповідати ствердно, спираючись на дотичну, але іншу норму.
```

Контекст подається блоками, кожен із заголовком `[chunk_id]`, назвою акта і
розділом — щоб модель мала що процитувати.

## 22. Набір тестових питань

Десять питань шести типів. Два з них — не вигадані складні випадки, а
**виміряні провали retrieval із ДЗ №2 і №3**.

| Тип | Скільки | Що перевіряє |
|---|---|---|
| `grounded` | 2 | базовий випадок, відповідь у контексті |
| `reformulated` | 1 | розмовне формулювання тієї ж норми |
| `multi_source` | 2 | потрібні дві статті одночасно |
| `weak_context` | 2 | retrieval **стабільно** дає хибні чанки |
| `out_of_scope` | 2 | питання поза корпусом — має спрацювати fallback |
| `general_trap` | 1 | модель знає відповідь із навчання, але корпус не містить |

Пастка окремо варта пояснення. Питання «скільки днів відпустки в Польщі?»
Claude знає без жодного контексту. Це робить вимогу «тільки з контексту»
не формальністю, а перевіркою, яку видно неозброєним оком: відповів —
промпт не працює.

Потрібен `ANTHROPIC_API_KEY` у середовищі. Ключ ніде не зберігається в
репозиторії й не потрапляє у вивід скриптів.

## 25. Результати

Десять питань × три версії промпта = 30 викликів, $0.85.

| Версія | Відмовилась там, де треба | Цитує джерело | Хибних відповідей |
|---|---|---|---|
| `v1` наївний | **0/6** | **0/4** | **6** |
| `v2` з правилами | 6/6 | 4/4 | 0 |
| `v3` фінальний | 6/6 | 4/4 | 0 |

Повні відповіді — [`outputs/rag_answers_examples.md`](outputs/rag_answers_examples.md),
порівняння версій — [`outputs/prompt_improvements.md`](outputs/prompt_improvements.md).

Наївний промпт відповів **на кожне** питання, де контексту бракувало: про
податки, про судовий збір, про відпустку в Польщі. Тобто гіпотеза
підтвердилась повністю — Claude знає українське трудове право й охоче
відповідає з пам'яті, якщо цього прямо не заборонити.

### Найважливіша знахідка

Питання «я щойно влаштувався, через скільки зможу піти у відпустку?»
виявилось не тим, чим здавалось.

`v1` відповів правильно по суті — «після шести місяців безперервної роботи» —
**і поставив посилання** на `zakon_pro_vidpustky_chunk_0006`. Виглядає як
зразкова grounded-відповідь.

Перевірка показала, що норма про шість місяців міститься у
`zakon_pro_vidpustky_chunk_0021`, а retrieval повернув чанки `0006`, `0026`
і `0007` — **у жодному її немає**. Модель узяла відповідь із навчання і
приписала їй цитату на чанк, який цього не підтверджує.

Це найнебезпечніший тип помилки в RAG: відповідь правильна, оформлена за
всіма правилами, з посиланням — і при цьому не випливає з наданого джерела.
Автоматична перевірка «чи є цитата» такого не ловить.

`v2` і `v3` відмовились і точно назвали, чого бракує: «немає положення
статті 10, яке визначає, після якого періоду безперервної роботи виникає
право». Це і є правильна поведінка.

### Перевірка на вигадані реквізити

| Версія | Згадано chunk_id | Поза контекстом | Неіснуючих |
|---|---|---|---|
| `v1` | 3 | 0 | 0 |
| `v2` | 26 | 0 | 0 |
| `v3` | 21 | 0 | 0 |

Жодна версія не вигадала неіснуючого `chunk_id`. Проблема `v1` була не у
фальшивих ідентифікаторах, а в тому, що **справжній ідентифікатор
підставлявся під твердження, якого в тому чанку немає**.

## 26. Prompt improvements

### Покращення 1: `v1` → `v2` — правила замість побажань

**Проблема.** Наївний промпт («відповідай, використовуючи наданий контекст»)
не спрацював узагалі: 6 вигаданих відповідей із 10, 0 цитат із 4 можливих.

**Що змінено.** Три явні правила: відповідати виключно з контексту й не
використовувати зовнішні знання «навіть якщо впевнений»; при нестачі
інформації — фіксована фраза; завжди цитувати статтю і `chunk_id`.

**Результат.** 0/6 → **6/6** коректних відмов, 0/4 → **4/4** цитат,
6 → **0** хибних відповідей. Найбільший стрибок у всьому завданні.

### Покращення 2: `v2` → `v3` — перевірка релевантності перед відповіддю

**Проблема.** `v2` виправив коректність, але його відмови були
багатослівні, а сам промпт не пояснював моделі, **чому** контекст може
не підходити. Модель не знала, що чанки дібрано автоматичним пошуком.

**Що змінено.** Доданий явний порядок роботи: спершу перевірити, чи контекст
відповідає на питання, лише потім відповідати. Прямо сказано, що висока
схожість не означає наявність відповіді, а збіг слів не є відповіддю.
Заборона конкретизована прикладами (інші країни, податкове й процесуальне
право). Доданий окремий режим часткової відповіді — назвати дотичну норму,
не видаючи її за відповідь.

**Результат.** Коректність не змінилась — вона вже була максимальною.
Змінилась економіка й читабельність:

| | `v1` | `v2` | `v3` |
|---|---|---|---|
| Середній вихід, токенів | 1223 | 622 | **573** |
| Середня довжина відповіді, символів | 2435 | 1301 | **1180** |
| Вартість 10 питань | $0.375 | $0.232 | $0.243 |

Вихід удвічі коротший за `v1`. Це чесний, але скромний виграш — і його варто
називати саме так, а не видавати за покращення точності.

### Покращення 3: виправлення не промпта, а **методики вимірювання**

**Проблема.** Перша версія оцінювання вважала, що переформульоване питання
завжди має відповідь у контексті, і тому позначала відмову `v2`/`v3` на
питанні 3 як помилку. Це був хибний висновок в оцінювачі, а не в моделі:
насправді retrieval не знайшов потрібної норми, і відмова була правильною.

**Що змінено.** Введено окреме поле `context_sufficient`, значення якого
**перевірене по кешу контексту**, а не виведене з типу питання. Тип питання
описує запит, достатність контексту — результат пошуку; змішувати їх не можна.

**Результат.** Підсумкові цифри змінились із «0/3 відмов, 3 хибні» на
«**0/6 відмов, 6 хибних**» для `v1`. Тобто хибне вимірювання **вдвічі
занижувало** реальну кількість галюцинацій наївного промпта.

## 27. Висновки

**Заборона на зовнішні знання — не формальність.** Без явного правила модель
відповіла на 6 із 6 питань, де контексту не було. Вона знає українське
трудове право; RAG-обгортка без жорсткої інструкції просто не працює.

**Цитата не доводить обґрунтованості.** Головна знахідка завдання: `v1` дав
правильну відповідь із посиланням на чанк, який її не містить. Перевірка
наявності `chunk_id` у відповіді — необхідна, але недостатня. Реальна
перевірка вимагає зіставлення твердження з текстом чанка.

**Reranking несподівано дав сигнал впевненості.** Скори cross-encoder'а
розтягнулись від 0.022 до 0.998 замість стиснутої смуги bi-encoder'а.
Питання поза корпусом чисто відсікаються порогом, але середня смуга
0.13–0.41 змішана, тож поріг лишається фільтром, а не суддею.

**Межа лишилась там само, де й була.** Питання 6 про відпустку за свій
рахунок провалилось у ДЗ №2, ДЗ №3 і тепер у ДЗ №4 — просто на кожному етапі
по-різному. Тут система вже не дає хибної відповіді, а чесно відмовляється,
що краще; але відповіді користувач так і не отримав. Причина незмінна:
стаття 25 розрізана на 10 чанків-переліків. **Дефект чанкінгу з ДЗ №1
пройшов крізь усі три наступні етапи недоторканим.**

**Що варто зробити далі.** Найкорисніше — не ще одна ітерація промпта, а
повернення до чанкінгу: contextual retrieval для статей-переліків. Друге за
цінністю — автоматична перевірка обґрунтованості: другий виклик моделі, що
зіставляє кожне твердження відповіді з текстом процитованого чанка.

# Домашнє завдання №5 — Інтеграція зовнішніх інструментів

Чат-бот отримує доступ до джерел, яких у корпусі немає й бути не може.

## 28. Чому саме ці інструменти

Вибір не абстрактний — він закриває **виміряну діру**. У ДЗ №4 два з десяти
питань отримали чесну відмову:

| Питання ДЗ №4 | Що відповів RAG |
|---|---|
| «Скільки податків утримується з зарплати?» | відмова — податкове право поза корпусом |
| «Яке мито треба сплатити, щоб подати позов?» | відмова — судовий збір поза корпусом |

І ще один випадок, менш очевидний: на «що таке мінімальна заробітна плата»
модель дала визначення зі статті 3 Закону «Про оплату праці» — **без суми**.
Причина структурна: закон визначає *поняття* й прямо каже, що розмір
встановлюється окремим законом. Сама сума щороку задається Законом про
Держбюджет, якого в корпусі немає й не може бути — він змінюється щороку,
а корпус статичний.

Це і є межа retrieval як такого. Її не посунути ні кращим чанкінгом, ні
reranking'ом.

## 29. Три інструменти

| Інструмент | Тип | Закриває |
|---|---|---|
| `get_statutory_amount` | read | дані, що змінюються за розкладом, якого корпус не відстежує |
| `calculate_vacation_entitlement` | read / обчислення | арифметику за датами конкретної людини |
| `submit_leave_request` | **write** | дію, а не пошук |

Кожен обраний під свою причину «чому інструмент, а не retrieval». Разом вони
покривають три різні типи задач, які пошук не виконує в принципі.

### `get_statutory_amount`

**Мета.** Повертає чинну на задану дату суму державного показника: мінімальна
зарплата (місячна й погодинна), прожитковий мінімум для працездатних осіб,
судовий збір у трудовому спорі.

**Коли викликати.** Коли користувач питає конкретну **суму в гривнях**.

**Коли НЕ викликати.** Коли питання про визначення поняття, порядок
нарахування чи права працівника — це є в законодавстві, туди й треба йти.

**Input contract**

```json
{
  "indicator": "minimum_wage_monthly | minimum_wage_hourly | subsistence_minimum_able_bodied | court_fee_labour_claim",
  "on_date": "2026-09-02 | null"
}
```

**Output contract**

```json
{
  "indicator": "minimum_wage_monthly",
  "label": "Мінімальна заробітна плата (місячна)",
  "value": 8647,
  "unit": "UAH/month",
  "effective_from": "2026-01-01",
  "effective_to": null,
  "on_date": "2026-09-02",
  "legal_basis": "Стаття 3 Закону України «Про оплату праці»; розмір встановлюється Законом про Держбюджет",
  "data_status": "fixture",
  "disclaimer": "Демонстраційний набір даних…"
}
```

### `calculate_vacation_entitlement`

**Мета.** Рахує накопичені й залишкові дні щорічної відпустки для конкретної
людини станом на дату, плюс чи є право на повну відпустку (шість місяців
безперервної роботи, стаття 10).

**Коли викликати.** Коли в питанні є дата працевлаштування або йдеться про
«скільки днів я вже накопичив».

**Коли НЕ викликати.** Для питань про тривалість відпустки взагалі — це норма
статті 6, її дає база знань.

**Input:** `employment_start_date`, `as_of_date` (опційно), `annual_days`
(24–59, за замовчуванням 24), `used_days`.
**Output:** `days_worked`, `months_worked`, `accrued_days`, `remaining_days`,
`eligible_for_full_leave`, `legal_basis`.

### `submit_leave_request` (write)

**Мета.** Подає заявку на відпустку. Єдиний інструмент, що **змінює дані**.

**Гейт підтвердження.** Виклик із `confirmed=false` повертає прев'ю зі
статусом `requires_confirmation` і **не записує нічого**. Запис відбувається
лише після повторного виклику з `confirmed=true`, і лише коли користувач
підтвердив явно. Це закладено і в схему інструмента, і в системний промпт.

## 30. Validation

Перевірка на Pydantic-моделях, а не рукописних `if`. Модель одночасно є
контрактом для Claude і фільтром на вході:

| Перевірка | Як реалізовано | Що відхиляє |
|---|---|---|
| Обов'язкові поля | `required` у схемі + Pydantic | виклик без `indicator` |
| Закритий перелік значень | `Literal[...]` → JSON enum | `indicator: "drop table"` |
| Формат ID | `field_validator` + регулярка `^emp_\d{3,6}$` | `employee_id: "123"` |
| Діапазони чисел | `Field(ge=…, le=…)` | `days: 500` |
| Логіка дат | власні валідатори | дата працевлаштування в майбутньому |
| Write вимагає підтвердження | `confirmed: bool` + гілка в коді | запис без згоди користувача |

**Про raw SQL.** Жоден інструмент не приймає вільного тексту, що доходить до
рушія запитів. Усі параметри — типізовані скаляри, дати або закриті enum'и.
Поверхні для ін'єкції просто немає: модель фізично не може передати запит,
вона може лише обрати одне зі значень переліку.

### Одна деталь, що спливла на практиці

`strict: true` в Anthropic API **не приймає** ключових слів `minimum` і
`maximum`, які Pydantic генерує з `ge`/`le`. Перший запит упав із 400:

```
tools.2.custom: For 'integer' type, properties maximum, minimum are not supported
```

Рішення — не прибирати обмеження, а **розділити контракт на два шари**: схема
для API описує *форму* аргументів, Pydantic перевіряє їхні *значення* під час
виконання. Межі діапазону переносяться в текст опису, щоб модель усе одно про
них знала. Захист від цього не слабшає, а посилюється: навіть якби API
пропустив `days: 500`, Pydantic його відкине.

## 31. Оркестрація

RAG виведений у модель **як ще один інструмент** — `search_labour_law`. Тобто
маршрутизація стала одним рішенням, яке модель ухвалює, бачачи всі варіанти
одразу:

```
питання
  ↓
claude-opus-5 обирає джерело
  ├─ search_labour_law ......... норма права
  ├─ get_statutory_amount ...... сума у гривнях
  ├─ calculate_vacation_... .... розрахунок за датами
  └─ submit_leave_request ...... дія (через підтвердження)
  ↓
валідація Pydantic → виконання → нормалізований JSON
  ↓
результат повертається моделі як tool_result
  ↓ (цикл повторюється, доки модель викликає інструменти)
відповідь із посиланнями на джерело кожного факту
```

Цикл написаний вручну, а не через SDK-шний tool runner. Дві причини: runner
у беті, а тут потрібен повний слід кожного кроку — сирі аргументи від моделі,
результат валідації, відповідь джерела. Ручний цикл робить цей слід
природним виходом, а не тим, що доводиться відновлювати постфактум.

## 32. Результати

Повні приклади — [`outputs/tool_examples.md`](outputs/tool_examples.md).

П'ять сценаріїв, кожен ізолює одне рішення маршрутизації. Окремо варто
відзначити **четвертий**: там правильна поведінка — **не викликати** жоден
зовнішній інструмент. Шар, що смикає інструменти на кожне питання, зламаний
рівно так само, як той, що не смикає їх ніколи, — і перевірити це можна лише
сценарієм, де інструменти мають лишитись осторонь.

## 33. Чесно про дані

`data/reference/statutory_amounts.json` — **фікстура, а не звірені значення**.
Реальні суми мінімальної зарплати й прожиткового мінімуму щороку встановлює
Закон про Держбюджет, і я не мав змоги звірити їх на момент написання.

Файл несе поле `data_status: "fixture"` разом із текстом застереження, і
**інструмент повертає їх у відповідь**, а системний промпт зобов'язує модель
попередити користувача. Це видно в прикладах: у відповіді про мінімальну
зарплату модель сама додала попередження, що дані демонстраційні.

Так зроблено свідомо. Помічник із трудового права, який упевнено називає
неправильну мінімальну зарплату, шкідливіший за того, хто чесно каже «не
знаю». У продакшні цей файл замінюється на завантаження з офіційного джерела —
структура інструмента при цьому не змінюється взагалі.

## 34. Як запустити

Інструмент напряму, без моделі:

```bash
python scripts/external_tool.py get_statutory_amount '{"indicator":"minimum_wage_monthly"}'
```

Побачити всі схеми, які отримує модель:

```bash
python scripts/external_tool.py --schemas
```

Через оркестрацію:

```bash
python scripts/rag_agent.py "яка зараз мінімальна заробітна плата"
```

Відтворити звіт:

```bash
python scripts/run_tool_examples.py
```

# Домашнє завдання №6 — Agentic workflow

Той самий помічник, але рішення про маршрут перенесене з моделі в код.

## 35. Use case

**Помічник працівника з трудових питань.** Один вхід — питання природною
мовою; далі система сама визначає, що це за запит, і веде його потрібним
маршрутом: норма права, державна сума, персональний розрахунок або подання
заявки на відпустку.

У ДЗ №5 вибір робила модель. Тут той самий вибір роблять правила — і оскільки
обидва роутери працюють над **тими самими інструментами**, їх можна порівняти
напряму. Це перетворює завдання з навчальної вправи на вимірювання.

## 36. Схема workflow

```
                        питання працівника
                               │
                    ┌──────────▼──────────┐
                    │   ROUTER (правила)  │
                    │  keyword matching   │
                    └──────────┬──────────┘
        ┌──────────┬───────────┼───────────┬──────────┐
        ▼          ▼           ▼           ▼          ▼
  statutory_   legal_norm  personal_   leave_    clarification
    amount                calculation  request
        │          │           │           │          │
        ▼          ▼           ▼           ▼          ▼
  extract_    extract_    extract_    extract_    compose_
   slots       slots       slots       slots    clarification
        │          │           │           │          │
        ▼          ▼           ▼           ▼          ▼
  lookup_     search_    check_slots  check_slots   ask user
  amount      knowledge       │           │
        │      _base          ▼           ▼
        │          │     calculate_  calculate_
        │          │     entitlement entitlement
        │          │           │           │
        │          │           │           ▼
        │          │           │      preview_request
        │          │           │           │
        └──────────┴───────────┴───────────┘
                               │
                               ▼
                     compose_answer (шаблон)
                               │
                               ▼
                        FlowState → відповідь

  Переходи маршруту:
  будь-який маршрут ──[слотів бракує]──► ask_user
  leave_request ──[не підтверджено]──► очікування підтвердження
```

## 37. Routes

П'ять маршрутів. Порядок перевірки правил має значення: від найбільш
специфічного до найзагальнішого, інакше «подай заявку на **відпустку**»
впала б у `legal_norm`, бо там теж є ключ «відпустк».

| Маршрут | Тригери | Кроки |
|---|---|---|
| `leave_request` | «подай заявку», «оформити відпустку» | 5 кроків, з підтвердженням |
| `personal_calculation` | «накопич», «я працюю з» | 4 кроки |
| `statutory_amount` | «мінімальна зарплата», «прожитковий мінімум», «судовий збір» | 3 кроки |
| `legal_norm` | «стаття», «закон», «відпустк», «звільнен», «робочий час»… | 3 кроки |
| `clarification` | нічого не збіглося | 1 крок, питає користувача |

## 38. Tools

Інструменти не вигадувались заново — це ті самі, що в ДЗ №5, і вони вже
працюють на фікстурах, тобто повертають фіксований результат:

| Інструмент | Що повертає |
|---|---|
| `get_statutory_amount` | суму з довідника `data/reference/statutory_amounts.json` |
| `calculate_vacation_entitlement` | накопичені та залишкові дні відпустки |
| `submit_leave_request` | прев'ю заявки або запис після підтвердження |
| `search_knowledge_base` | top-2 чанки з FAISS-індексу, з відкатом на заглушку |

Останній має **відкат**: якщо індексу немає на диску, повертається фікстура.
Це свідомо — workflow має демонструватись без 1.1 ГБ ваг моделі.

## 39. State

Один об'єкт `FlowState` живе весь прогін і накопичує все, що сталося:

| Поле | Що зберігає |
|---|---|
| `user_goal` | вихідне питання |
| `selected_route` | обраний маршрут |
| `route_reason` | **чому** саме він — рядок із ключем, що спрацював |
| `slots` | витягнуті сутності: `employee_id`, дати, кількість днів, індикатор |
| `plan` | послідовність кроків маршруту |
| `steps` | що виконано: крок, інструмент, вхід, спостереження, успіх |
| `observations` | результати кроків окремим списком |
| `needs_user_input` | чого бракує, якщо workflow зупинився |
| `final_answer` | підсумкова відповідь |

**Стан справді використовується між кроками**, а не просто логується.
У маршруті `leave_request`: крок 2 знаходить працівника за `employee_id` зі
слотів → крок 3 бере його дату працевлаштування й рахує накопичені дні →
крок 4 порівнює запитану кількість днів із накопиченими й позначає
перевищення. Кожен наступний крок читає те, що поклав попередній.

## 40. Переходи маршруту

Найцікавіше в роутері — не вибір гілки, а що відбувається, коли гілку обрано,
а даних бракує. Питання «Хочу подати заявку на відпустку» коректно потрапляє
в `leave_request`, але без `employee_id`, дати й кількості днів виконати його
неможливо:

```
Route: leave_request
Plan: extract_slots → check_required_slots → calculate_entitlement
      → preview_request → compose_answer → ask_user
Step 2: check_required_slots  [слотів бракує]
Final answer: Щоб продовжити, вкажіть, будь ласка, ідентифікатор
              працівника у форматі emp_001.
```

До плану **дописується** крок `ask_user`, стан позначає крок як непройдений,
і workflow зупиняється замість того, щоб упасти або вигадати дані.

## 41. Порівняння з LLM-маршрутизацією

Головний результат. Ті самі шість питань із ДЗ №5, збережені рішення моделі
з `outputs/tool_runs.json`:

| | Значення |
|---|---|
| Основний маршрут вгадано | **6 із 6** |
| Покрито всі джерела, які взяла модель | **4 із 6** |

Різниця між цими числами і є ціною детермінованого роутера.

**Де правила не гірші.** Коли питання містить характерне слово — «мінімальна
заробітна плата», «подай заявку», дата в тексті — дешевий роутер влучає так
само точно, як модель, за нуль доларів і мілісекунди замість секунд.

**Де правила програють.** На питанні «що таке мінімальна зарплата **і скільки
вона зараз**» модель викликала **два** джерела: норму з бази знань і суму з
довідника. Правила обирають рівно один маршрут — половина відповіді
втрачається. Це не помилка в ключових словах, а обмеження самої конструкції
«один вхід → одна гілка».

**Друге обмеження — перефразування.** Ключі покривають те, що ми передбачили.
Питання, сформульоване інакше, падає в `clarification`, де модель зрозуміла б
його без підказок.

| | Правила | Модель |
|---|---|---|
| Вартість запиту | $0 | ~$0.02–0.04 |
| Затримка | мілісекунди | секунди |
| Відтворюваність | побайтова | ні |
| Пояснюваність | рядок із причиною | треба довіряти |
| Нові формулювання | падають у clarification | зазвичай розуміє |
| Кілька джерел одразу | не вміє | вміє |

**Практичний висновок — це не «або-або».** Правила добре працюють як швидкий
шар для передбачуваних намірів, модель — як запасний варіант для решти. Тоді
типові питання коштують нуль, а нетипові все одно отримують відповідь.
